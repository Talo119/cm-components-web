# 0022: Form

- **Status:** Implemented
- **Date:** 2026-11-10
- **Kind:** Composite
- **Depends on:** [0000](./0000-architecture.md), [0001](./0001-button.md), [0005](./0005-inputs.md), [0006](./0006-select.md), [0007](./0007-radio-group.md), [0008](./0008-switch.md), [0009](./0009-slider.md), [0010](./0010-rating.md), [0014](./0014-autocomplete.md)

## Purpose

Builds a form from a list of field definitions, such as a sign-up form, a profile page or the filters of a report. Each field definition names a value and picks one of the library's field components. Form keeps the values, validates them, shows each error under its field, moves focus to the first invalid field, and calls `onSubmit` with the values when they're valid.

Without it, each project wires every field's `value`, `onChange`, `error` and `helperText`, writes the same required-field checks, and lays out the submit button. The field components already share the same field props ([`fieldProps.ts`](../../src/components/fieldProps.ts)), so Form can drive all of them the same way.

**Use it for:** forms of up to about twenty fields with simple rules, such as required fields, lengths, ranges and checks across fields. Settings pages and dialogs that save a record.

**Don't use it for:**

- Forms with repeating groups, steps, or fields added and removed by the user. Use the field components directly, with a form library such as React Hook Form. See [State management](#state-management).
- A single search field or filter. Use TextField or Autocomplete on its own.
- Editing values inline in a table. That's out of scope for Table and Form.

## Usage

```tsx
import { Button, Form } from '@cmotino/cm-web-components'
import type { FormField } from '@cmotino/cm-web-components'

interface Profile {
  name: string
  email: string
  role: string | null
  bio: string
  newsletter: boolean
}

const fields: FormField<Profile>[] = [
  { name: 'name', type: 'text', label: 'Name', required: true, autoComplete: 'name' },
  { name: 'email', type: 'email', label: 'Email', required: true, autoComplete: 'email' },
  {
    name: 'role',
    type: 'select',
    label: 'Role',
    required: true,
    options: [
      { value: 'admin', label: 'Admin' },
      { value: 'editor', label: 'Editor' },
    ],
  },
  { name: 'bio', type: 'textarea', label: 'Bio', maxLength: 280, span: 2 },
  { name: 'newsletter', type: 'switch', label: 'Send me the newsletter', span: 2 },
]

<Form
  aria-label="Profile"
  fields={fields}
  defaultValues={{ name: '', email: '', role: null, bio: '', newsletter: false }}
  columns={2}
  submitLabel="Save"
  actions={<Button variant="text" onClick={onCancel}>Cancel</Button>}
  errors={serverErrors}
  onSubmit={async (values) => {
    const result = await saveProfile(values)
    if (!result.ok) setServerErrors(result.fieldErrors)
  }}
/>
```

## API

`Form` is a component of this library, in `src/components/Form/`. It renders a `<form>` and the library's field components, not MUI's directly.

```ts
export { Form } from './Form.tsx'
export type { FormProps, FormField, FormValues, FormMessages } from './Form.types.ts'
```

| Prop | Type | Default | Required | Description |
| --- | --- | --- | --- | --- |
| `fields` | `readonly FormField<Values>[]` | | Yes | The fields, in display order |
| `onSubmit` | `(values: Values, event: FormEvent<HTMLFormElement>) => void \| Promise<void>` | | Yes | Called with the values when every visible field is valid. Replaces the HTML `onSubmit` |
| `values` | `Values` | `undefined` | No | Controlled values |
| `defaultValues` | `Values` | Each field's empty value | No | Initial values when uncontrolled. See Empty values |
| `onValuesChange` | `(values: Values, name: keyof Values) => void` | `undefined` | No | Called when the user changes a field, with every value and the field's name |
| `errors` | `Partial<Record<keyof Values, string>>` | `undefined` | No | Errors from outside Form, such as the server's. Shown under their fields |
| `validateOn` | `'submit' \| 'blur' \| 'change'` | `'submit'` | No | When a field is first validated. See Validation |
| `submitLabel` | `ReactNode` | `'Submit'` | No | The submit button's text |
| `actions` | `ReactNode` | `undefined` | No | More buttons before the submit button, such as Cancel |
| `submitting` | `boolean` | `undefined` | No | Controlled submitting state. Without it, Form is submitting while the promise from `onSubmit` is pending |
| `disabled` | `boolean` | `false` | No | Disables every field and the submit button |
| `columns` | `number` | `1` | No | The number of columns from the `sm` breakpoint up. Below it, there's always one |
| `messages` | `Partial<FormMessages>` | English messages | No | The text of the built-in validation errors |
| `slotProps` | See below | `undefined` | No | Props for inner parts |

`Form` also takes `sx`, `className`, `ref`, `aria-label`, `noValidate` and other props of a `<form>`, which reach the root `<form>`, as the architecture spec requires. It's generic, as `Form<Values extends FormValuesOf<Values>>`, and `Values` is inferred from `defaultValues` or `values`, or from `fields` typed as `FormField<Profile>[]`, as in the example. Without any of them, pass it explicitly: `<Form<Profile> ...>`.

**Typing `Values`:** the constraint is `FormValuesOf<Values>`, `{ [Name in keyof Values]: unknown }`, rather than `FormValues`. With `FormValues`, an `interface` such as `Profile` doesn't fit, because it has no index signature, and inferring from `defaultValues={{ agree: false }}` keeps the literal type `false`, because `FormValue` includes `boolean`. A value that isn't a `FormValue` has no field type that fits it, so it can't get a field. `FormValues` stays exported, for the type of a form's values in general.

```ts
export type FormValue = string | number | boolean | null | readonly (string | number)[]
export type FormValues = Record<string, FormValue>

export interface FormProps<Values extends FormValuesOf<Values>>
  extends Omit<ComponentProps<'form'>, 'onSubmit' | 'onChange' | 'children' | 'defaultValue'> {
  fields: readonly FormField<Values>[]
  onSubmit: (values: Values, event: FormEvent<HTMLFormElement>) => void | Promise<void>
  values?: Values
  defaultValues?: Values
  onValuesChange?: (values: Values, name: keyof Values) => void
  errors?: Partial<Record<keyof Values, string>>
  validateOn?: 'submit' | 'blur' | 'change'
  submitLabel?: ReactNode
  actions?: ReactNode
  submitting?: boolean
  disabled?: boolean
  columns?: number
  messages?: Partial<FormMessages>
  sx?: SxProps<Theme>
  slotProps?: {
    /** The grid `<div>` around the fields. */
    fields?: ComponentProps<'div'>
    /** Every field's wrapper `<div>`, the grid cell. */
    field?: ComponentProps<'div'>
    /** The row of buttons. */
    actions?: ComponentProps<'div'>
    /** The submit Button. */
    submit?: Partial<Omit<ButtonProps, 'type' | 'loading'>>
  }
}
```

### State management

This answers the [roadmap question](./roadmap.md#questions-for-later-specs) for Form: **Form keeps its state internally, with no form library.**

- **No new dependency.** React Hook Form would become a peer dependency of every project, including those that never use Form, against [section 4 of the architecture spec](./0000-architecture.md#4-dependencies).
- **Form's job is small.** It maps field definitions to field components and checks a few rules. That's a few hundred lines with `useState`, and the React Compiler handles the re-renders.
- **The field components stay usable on their own.** A project with complex forms uses TextField, Select and the rest with React Hook Form's `Controller`, without Form. The documentation must show this.
- **Revisit if** consumers need field arrays, steps, or validation schemas such as Zod. Those are the features where a form library pays off.

### Fields

Each field's `type` picks a component, and must fit the type of its value in `Values`. A field whose type doesn't fit its value fails to compile. A field fits when what it produces fits the value, and the value's non-null part is something it can show: text fields need `string`, so a value limited to some strings, such as `'free' | 'pro'`, takes `select` or `radio`, whose `options` are typed with those strings. `number` and `rating` can be empty, so their value must allow `null`.

| `type` | Component | Value type | Empty value | Field-specific props |
| --- | --- | --- | --- | --- |
| `text`, `email`, `password`, `tel`, `url` | TextField with that `type` | `string` | `''` | `placeholder`, `autoComplete`, `minLength`, `maxLength` |
| `textarea` | TextField with `multiline` | `string` | `''` | `placeholder`, `minLength`, `maxLength`, `rows` |
| `number` | TextField with `type="number"` | `number \| null` | `null` | `placeholder`, `min`, `max`, `step` |
| `select` | Select ([0006](./0006-select.md)) | `string \| number \| null` | `null` | `options` |
| `radio` | Radio group ([0007](./0007-radio-group.md)) | `string \| null` | `null` | `options`, `row` |
| `autocomplete` | Autocomplete ([0014](./0014-autocomplete.md)) | `string \| number \| null`, or an array with `multiple` | `null` or `[]` | `options`, `multiple`, `placeholder` |
| `checkbox` | Checkbox ([0005](./0005-inputs.md)) | `boolean` | `false` | None |
| `switch` | Switch ([0008](./0008-switch.md)) | `boolean` | `false` | None |
| `slider` | Slider ([0009](./0009-slider.md)) | `number` | `min`, or `0` | `min`, `max`, `step`, `marks` |
| `rating` | Rating ([0010](./0010-rating.md)) | `number \| null` | `null` | `max`, `precision` |

Every field also takes:

| Prop | Type | Description |
| --- | --- | --- |
| `name` | A key of `Values` | The value the field edits. Also the input's `name` and the React key |
| `type` | See above | The component |
| `label` | `ReactNode` | The visible label and accessible name |
| `helperText` | `ReactNode` | Text under the field. An error replaces it while shown |
| `required` | `boolean` | The field must have a value that isn't empty. For `checkbox` and `switch`, it must be `true` |
| `disabled` | `boolean` | Disables the field |
| `validate` | `(value, values) => string \| undefined` | A custom check, run after the built-in ones. Returns the error, or `undefined` when valid |
| `hidden` | `(values: Values) => boolean` | Hides the field. A hidden field isn't validated, and keeps its value |
| `span` | `number` | How many columns the field takes. Defaults to `1`, and is capped at `columns` |
| `props` | The component's props | Any other prop of the field's component, such as `slotProps` or `sx` |

### Validation

- **Built-in checks,** in this order: `required`, then `minLength` and `maxLength`, then `min` and `max`, then the format of `email` and `url` fields. The first that fails gives the error, and `validate` runs only if they all pass.
- **When:** with `validateOn="submit"`, a field is first validated when the form is submitted. With `"blur"`, also when it loses focus. With `"change"`, also on every change. After a field has shown an error, it's revalidated on every change, so the error goes away as soon as it's fixed.
- **On submit:** Form calls `event.preventDefault()`, validates every visible field, and if any fails, shows the errors, moves focus to the first invalid field in display order, and doesn't call `onSubmit`.
- **External errors:** an entry in `errors` is shown under its field when the field has no error of its own. The consumer clears it, typically on the next submit or in `onValuesChange`.
- **Native validation:** the `<form>` has `noValidate` by default, so the browser's bubbles don't compete with Form's errors. `required` still reaches each input, so it's announced.

### Submitting

While submitting, the submit button shows MUI's `loading` state and is disabled, and the `<form>` has `aria-busy="true"`. A second submit is ignored. Uncontrolled, submitting ends when the promise from `onSubmit` settles. Form doesn't catch a rejected promise: it ends the submitting state and lets the rejection through.

### Resetting

A `<button type="reset">` in `actions` resets uncontrolled values to `defaultValues`, clears Form's errors, and calls `onValuesChange` once with the reset values and the first field's name. A controlled Form only clears its errors, and calls `onReset`, where the consumer resets `values`.

### Theme key

Form reads its props through `useThemeProps({ props, name: 'CmForm' })`, and styles its parts with MUI's `styled`, with `name: 'CmForm'` and the slots `root`, `fields`, `field` and `actions`. The class names `CmForm-root`, `CmForm-fields`, `CmForm-field` and `CmForm-actions` are added to those elements. The key is declared through module augmentation in `Form.types.ts`, as [0019](./0019-tabs.md#theme-key) does for `CmTabs`.

### Exceptions to the architecture spec

| Rule | Exception | Reason |
| --- | --- | --- |
| Section 2: remaining props reach the root | `onSubmit` has its own signature, with the values first | The values are what a consumer needs. The event is still passed |
| Section 2: `value`, `defaultValue` and `onChange` | Named `values`, `defaultValues` and `onValuesChange` | Named state, as section 2 allows, because a form holds many values. `onChange` stays the `<form>`'s native event |

`Form.tsx` starts with `'use client'`, because it keeps state, and is added to `tests/dist.test.ts`.

## Data shapes

```ts
type FieldKey<Values> = Extract<keyof Values, string>

/** One field definition. The `type` must fit the type of `Values[name]`. */
export type FormValuesOf<Values> = { [Name in keyof Values]: unknown }

export type FormField<Values extends FormValuesOf<Values>> = {
  [Name in FieldKey<Values>]: FieldFor<Name, Values[Name], Values>
}[FieldKey<Values>]

// FieldFor picks the allowed field types from the value's type, following the
// table under Fields. For example, a `boolean` value allows `checkbox` and
// `switch`, and a `string` value allows the text types, `textarea`, `select`,
// `radio` and a single `autocomplete`.

export interface FormMessages {
  required: string
  minLength: (min: number) => string
  maxLength: (max: number) => string
  min: (min: number) => string
  max: (max: number) => string
  email: string
  url: string
}
```

Default messages, in English: "This field is required", "Enter at least {min} characters", "Enter at most {max} characters", "Enter {min} or more", "Enter {max} or less", "Enter a valid email address", "Enter a valid URL".

## Variants and states

| Variant or state | Behavior or appearance |
| --- | --- |
| Default | The fields in a grid with `theme.spacing(2)` between them, then the actions row, `theme.spacing(3)` below the fields |
| `columns` greater than 1 | That many equal columns from `sm` up, one below. `span` makes a field wider |
| Actions row | `actions`, then the submit button, aligned to the end. The submit button is a `contained` Button |
| Field with an error | The field component's `error` state, with the error in place of `helperText` |
| Submitting | The submit button shows a spinner and is disabled. Fields stay enabled, so the user can read them |
| `disabled` | Every field and the submit button are disabled |
| Hidden field | Not rendered, and takes no grid cell |
| Empty | `fields={[]}`: only the actions row |

## Styling hooks

- **Theme keys:** `components.CmForm`, with the slots `root`, `fields`, `field` and `actions`, and default props for every Form prop. The fields use their own theme keys, such as `MuiTextField` and `MuiSelect`, and the submit button uses `MuiButton`.
- **Slots:** `fields`, `field`, `actions` and `submit`, as typed under API. A single field is reached through its `props`. The root is reached with `sx` and `className`.
- **Default look:** the library's field components and Button, laid out with CSS grid. Spacing comes from `theme.spacing` and breakpoints from `theme.breakpoints`. No color of its own.

## Accessibility

- **Semantics:** a `<form>`. With `aria-label` or `aria-labelledby`, it's a `form` landmark. Each field has the semantics of its component.
- **Keyboard:** each field works as in its own spec. `Enter` in a single-line text field submits the form, as in the browser. `Tab` follows display order, which is also the order in the grid.
- **Naming:** each field is named by its `label`. A field without a `label` needs `props['aria-label']`. Errors are linked to their inputs through `aria-describedby`, and invalid inputs have `aria-invalid="true"`, both from the field components.
- **Focus:** on a failed submit, focus moves to the first invalid field, so screen readers announce its label and error. Validation on blur or change doesn't move focus.
- **Required fields:** the label shows an asterisk, and the input has `required`, so it's announced as required.
- **Status:** `aria-busy="true"` on the form while submitting. Announcing success is the consumer's, such as with an Alert.

## Behavior and edge cases

- **Duplicate names:** React logs key warnings, and both fields edit the same value. Names must be unique.
- **A controlled Form whose `values` don't change:** the fields don't change either, as with any controlled input.
- **A `name` missing from `defaultValues`:** the field starts with its empty value, and the value is added on the first change.
- **Numbers:** an empty `number` field is `null`. A value the browser can't parse, such as `1e`, is also `null`, and fails `required`.
- **Values from hidden fields:** they're kept and passed to `onSubmit`. A consumer that doesn't want them drops them there.
- **Checks across fields,** such as "Confirm password": `validate` receives every value. Changing one field doesn't revalidate the other until it changes or the form is submitted.
- **Async checks,** such as "This email is taken": run them in `onSubmit`, and pass the result through `errors`.
- **Long forms:** there's no grouping into sections. Split them across Tabs or several Forms.
- **Narrow screens:** one column below `sm`, whatever `columns` is.
- **Without the library theme:** Form renders its fields with the surrounding MUI theme.
- **Server Components:** Form is a client component. `fields` can be built in a Server Component only without `validate` or `hidden`, which are functions.

## Acceptance criteria

- [ ] Renders a `<form>` with one field for each definition, in order, using the component listed for its `type`, labelled by its `label`.
- [ ] Uncontrolled, fields start from `defaultValues`, or their empty value, and typing updates them and calls `onValuesChange` with every value and the field's name.
- [ ] Controlled, fields show `values` and only change when the consumer updates them.
- [ ] Submitting with valid values calls `onSubmit` with the values and the event, and doesn't reload the page.
- [ ] Submitting with an empty required field shows the `required` message under it, sets `aria-invalid="true"`, moves focus to it, and doesn't call `onSubmit`.
- [ ] `minLength`, `maxLength`, `min`, `max`, `email` and `url` each give their message, and `validate` runs after them with the value and every value.
- [ ] With `validateOn="submit"`, no error shows before the first submit. With `"blur"`, an error shows when the field loses focus. With `"change"`, on change. An error goes away as soon as the field is fixed.
- [ ] An entry in `errors` shows under its field, and a field's own error wins over it.
- [ ] While the promise from `onSubmit` is pending, the submit button is in its loading state and the form has `aria-busy="true"`, and a second submit doesn't call `onSubmit`.
- [ ] `submitting`, `disabled`, `submitLabel` and `actions` work as described.
- [ ] A field with `hidden` returning `true` isn't rendered or validated, and its value is still passed to `onSubmit`.
- [ ] With `columns={2}`, fields sit in two columns from `sm` up, a field with `span={2}` takes the full row, and there's one column below `sm`.
- [ ] A reset button resets uncontrolled values to `defaultValues` and clears the errors.
- [ ] `messages` replaces the built-in messages.
- [ ] `ref` reaches the `<form>`, and `className`, `sx`, `aria-label` and other props, such as `data-*`, reach it too.
- [ ] `slotProps.fields`, `field`, `actions` and `submit`, and each field's `props`, reach their elements.
- [ ] The root, grid, field cells and actions row have the `CmForm-root`, `CmForm-fields`, `CmForm-field` and `CmForm-actions` classes.
- [ ] Type check: `Values` is inferred from `defaultValues`, a `name` that isn't a key fails, a `switch` field for a `string` value fails, and `onSubmit` receives `Values`.
- [ ] A project-level `CmForm.defaultProps.validateOn` of `'blur'` applies to every Form.
- [ ] A project-level `CmForm` `styleOverrides.actions` object changes the actions row.
- [ ] Type check: `createCmTheme({ components: { CmForm: { defaultProps: { columns: 2 }, styleOverrides: { fields: { gap: 8 } } } } })` compiles, and an unknown slot name fails.
- [ ] An instance-level `sx` value overrides the theme.
- [ ] Under another MUI theme, without `CmThemeProvider`, Form renders with that theme.
- [ ] Works with the keyboard as listed under Accessibility.
- [ ] Storybook has a story with every field type, one with two columns, one with errors from `errors`, one submitting, one disabled, one with a hidden field, one controlled, and one showing a theme override.
- [ ] `Form`, `FormProps`, `FormField`, `FormValues` and `FormMessages` are exported from `src/index.ts`, and `Form` is added to the public API and `'use client'` lists in `tests/dist.test.ts`.

## Out of scope

- An integration with React Hook Form, Formik or another form library.
- Validation schemas, such as Zod or Yup.
- Repeating groups of fields, and fields the user adds or removes.
- Steps, and sections with headings.
- File uploads, dates and times. They have no field component yet.
- A range `slider` with two values.
- An error summary at the top of the form.
- Warning before leaving a form with unsaved changes.
- Custom field types rendered by the consumer.

## Open questions

- **State management:** confirm the decision under [State management](#state-management): internal state now, and a form library only if field arrays, steps or schemas are needed.
- **Default messages:** they're in English, like MUI's own text. Decide whether projects in other languages pass `messages` each time, or set them once through `CmForm.defaultProps.messages`, which this spec already allows.
- **Custom fields:** a `type: 'custom'` with a `render` function would cover fields the library lacks, such as a date picker. Decide whether to add it now or wait for a consumer.
